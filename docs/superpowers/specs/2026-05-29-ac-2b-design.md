## 1. Problem

`utils.treat_runtimeparams` accepts ~50+ per-`/action`-call params (forecast data, MPC knobs,
deferrable/battery overrides, ML-action args, publish routing, secrets), documented today only
as prose across `passing_data.md` / `forecasts.md` / `mlforecaster.md` / `thermal_battery.md` /
`publish_data.md` — parse-hostile for openapi.json / LLM / tool consumers. Two source findings
reshape the naive "add them to `param_definitions.json`":

1. **`param_definitions.json` drives the GUI form** (`configuration_script.js:130` renders every
   section as editable fields). Runtime params there would appear as persistent config inputs
   (wrong) → maintainer-reject.
2. **The keys are heterogeneous**: genuinely runtime-only optimization knobs; runtime overrides of
   params already in `param_definitions.json`; per-call data payloads; ML-action args; output
   routing; secrets. Only ~12 are genuinely-runtime-only *optimization input knobs* that belong
   in a dedicated machine schema now.

## 2. Goal

Ship `src/emhass/static/data/runtime_params.json` describing the **~12 genuinely-runtime-only
optimization input knobs** (AC-2a entry convention; `Description`s from the docs), with
`param_definitions.json` and the GUI untouched. The parse-friendly runtime-input contract for
tool/LLM consumers and the prerequisite schema for AM-1b (structured `/action` request payload).

## 5. Concrete content — `runtime_params.json`

Entry convention = AC-2a (`friendly_name`, `Description` locale-neutral from the docs, `input`,
`default_value`, `unit` from the locked enum `W, Wh, kWh, ¤/kWh, €, %, fraction, °C, °, min, h, days, timesteps, count, s, none`).
Types/defaults verified vs `treat_runtimeparams` + the feature docs:

| param | input | default | unit | doc |
|---|---|---|---|---|
| `prediction_horizon` | int | 10 | timesteps | mpc.md |
| `soc_init` | float | null (→`battery_target_state_of_charge`) | fraction | cookbook/battery_aware_runtime_params.md |
| `soc_final` | float | null (→`battery_target_state_of_charge`) | fraction | mpc.md |
| `operating_timesteps_of_each_deferrable_load` | array.int | null | timesteps | passing_data.md |
| `alpha` | float | 0.5 | fraction | forecasts.md (now/current mixing) |
| `beta` | float | 0.5 | fraction | forecasts.md |
| `weather_forecast_cache` | boolean | false | none | forecasts.md (caching) |
| `weather_forecast_cache_only` | boolean | false | none | forecasts.md |
| `adjusted_pv_model_max_age` | float | 24 | h | forecasts.md (model caching) |
| `open_meteo_cache_max_age` | int | 30 | min | forecasts.md (open-meteo caching) |
| `def_current_state` | array.boolean | null | none | passing_data.md |
| `def_load_config` | object (+ externalDocs → thermal_battery.md) | null | none | thermal_battery.md |

Example entry:
```json
"soc_init": {
  "friendly_name": "Initial battery state of charge",
  "Description": "Current battery SOC as a fraction in [0,1] (NOT percent). Clamped to [battery_minimum_state_of_charge, battery_maximum_state_of_charge]; out-of-bounds warns and falls back to battery_target_state_of_charge. See passing_data.md / cookbook/battery_aware_runtime_params.md.",
  "input": "float",
  "default_value": null,
  "unit": "fraction"
}
```
`def_load_config` carries `{"externalDocs": {"description": "Thermal load / thermal-battery config", "url": "docs/thermal_battery.md"}}` and `input:"object"` — the nested thermal schema is NOT inlined.

**Borderline (flag in PR / fork finalises):**
- `time_zone` — docs call it a Retrieve-HASS config param overridable at runtime; key-diff says it's in neither schema. **Verify** whether it's a config override (→ exclude, AM-1b refs) or runtime-only (→ include). Excluded from the table pending verification.
- `def_load_config` — include-as-linked-object (recommended, so consumers know it exists) vs drop entirely.
- `adjusted_pv_model_max_age` / `open_meteo_cache_max_age` — confirm they are runtime-only (not config entries) in the source scan (§6).

## 6. Test strategy + completeness gate

TDD. `tests/test_runtime_params.py`:
1. `runtime_params.json` parses.
2. Every entry has `friendly_name`, `Description`, `input`, `default_value`, `unit`.
3. `input` ∈ known vocabulary; `unit` ∈ locked enum.
4. The expected keys are all present (guards drops).

**Completeness gate (the "did we forget anything" full-source scan — user-requested):** the fork
session MUST scan the entire `treat_runtimeparams` in `utils.py` — **all `set_type` branches +
the `forecast_key` list + the `ml_param_defs` table** (the earlier `runtimeparams.get/[]/in`
regex was partial) — enumerate every accepted runtime key, and classify each into: runtime-only
optimization knob (→ this file), config-override (→ AM-1b refs param_definitions), data/ML payload
(→ AM-1b), output (→ AC-2c), §4.1 config key (→ AM-7), secret (excluded). Any key that doesn't fit
a bucket → STOP and surface (don't silently drop). This locks the §5 table against source truth
before the PR.

`python -m pytest` green; `python -m ruff` clean (no `uvx` — `python -m ruff`).

- Runtime overrides of existing config params → already in `param_definitions.json`; AM-1b refs.
- Data payloads (forecast lists) + ML-action args → AM-1b `/action`.
- §4.1 config-key → param_def SoT alignment → AM-7.

- `def_load_config` nested thermal schema → linked to `thermal_battery.md`, not inlined (its own schematization is a separate effort if ever).
