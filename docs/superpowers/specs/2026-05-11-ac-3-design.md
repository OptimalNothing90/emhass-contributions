# AC-3 — /api/v1/last-run JSON endpoint — Design

**Date:** 2026-05-11
**Card:** `AC-3` (board/items.json)
**Issue:** None (draft card; threat-model agreed in Discussion [#808](https://github.com/davidusb-geek/emhass/discussions/808))
**Audit source:** None — item body carries line citations vs upstream master @ `6537c47` (verified 2026-04-28)
**Target repo:** `davidusb-geek/emhass` (via `OptimalNothing90/emhass` fork)
**Branch:** `feat/ac-3-last-run`
**Effort:** S
**Phase / Priority:** Phase 3 / P1
**Goal-fit:** LLM-ready

## 1. Problem

EMHASS optimization runs leave no easily-queryable trace of metadata. The CSV `opt_res_latest.csv` holds the plan-output columns but says nothing about *how* the run went: how long each stage took, whether the solve succeeded or hit infeasibility, when it ran, which action was invoked, what EMHASS version was on the wire. Consumers building dashboards, LLM-driven explainers, watchdogs, or health checks have to either parse log files or guess from CSV timestamps. There is no machine-readable "what just happened" surface.

## 2. Goal

Ship `GET /api/v1/last-run` — a read-only JSON endpoint that returns metadata about the most recent optimization run with consistent always-200 envelope (`status` enum: `no-run` / `ok` / `infeasible` / `error`). State lives in a new `src/emhass/last_run.py` module (in-memory cache plus write-through to `<data_path>/last_run.json`), populated from `command_line.py` optim action wrappers so both CLI and Flask invocations participate. The endpoint becomes the foundation for AC-4 (`/healthz` reads `last_run.is_recent()`), future LLM explainer skills, and any consumer that needs run-aware behavior.

## 3. Decisions

| # | Decision | Source |
|---|----------|--------|
| D1 | **State persistence model: in-memory + file write-through to `<data_path>/last_run.json`.** In-memory cache for fast reads; file write after every recorded run for restart-safety. Read-on-startup if file exists. Q1 brainstorm. | session 2026-05-11 |
| D2 | **State lives in a new module `src/emhass/last_run.py`** (record / read / is_recent helpers). NOT in `command_line.py` (would couple optim layer to HTTP concerns) and NOT in `web_server.py` (would skip CLI users). The module is the single source of truth; both surfaces import it. Q2 brainstorm. | session 2026-05-11 |
| D3 | **Always-200 response with `status` enum field.** Four discriminator values: `no-run` / `ok` / `infeasible` / `error`. Other fields nullable when no run yet. LLM-/Skill-friendly (single parseable shape), simpler consumer code than 200-vs-404 branching. Q3 brainstorm. | session 2026-05-11 |
| D4 | **Response shape — 9 fields:** `status`, `timestamp` (ISO 8601 UTC), `action` (URL-form string: `"dayahead-optim"` / `"naive-mpc-optim"` / `"perfect-optim"` — matches the `/action/<name>` URL fragment, not the Python function name), `stage_times` (dict of stage → seconds), `duration_total_seconds` (**wall-clock** from action-wrapper entry to record-call — includes pre/post phases outside the per-stage timers, not just `sum(stage_times)`), `emhass_version` (from `importlib.metadata`), `schema_version` (from `EMHASS_SCHEMA_VERSION` per AC-1 / #835), `infeasible` (bool), `error_message` (string or null). Nullable fields when status=`no-run`. | session 2026-05-11 |
| D5 | **Depend on PR #835 (AC-1)** for `EMHASS_SCHEMA_VERSION` import. `from emhass.command_line import EMHASS_SCHEMA_VERSION` directly. PR body declares dependency; fork-session sequences after #835 merge (parallel-prep allowed: develop locally branched off `docs/ac-1`, rebase on master post-merge before push). Q4 brainstorm. | session 2026-05-11 |
| D6 | **No auth on the endpoint.** Consistent with the 9 existing web_server.py routes (none have auth today). Maintainer threat-model #808 ruled out auth-bypass — that means don't *weaken* existing auth, not "add auth here". Stage_times are performance-telemetry, not user-data. Q5 brainstorm. | Discussion #808 |
| D7 | **Capture point: `command_line.py` action wrappers** (`dayahead_forecast_optim`, `naive_mpc_optim`, `perfect_optim` — verify exact names in Phase 2 source-trace). Both CLI invocations and Flask `/action/<name>` route through these wrappers, so a single instrumentation point covers both surfaces. | D2 follow-through |
| D8 | **Thread-safety via `threading.Lock` inside `last_run.py`.** Flask may run multi-worker (gunicorn config exists). Lock guards the in-memory cache and the file write. Single-writer-multi-reader pattern. | observed Flask deployment patterns |
| D9 | **No-run state is observable, not error.** First boot after EMHASS install with empty `<data_path>/last_run.json` returns 200 with `status: "no-run"`. Consumers learn "endpoint up, nothing to report" — distinct from 503 (service not ready) which is AC-4 /healthz semantics. | D3 follow-through |
| D10 | **Cache-Control: `no-store` on the response.** State changes between requests; caching middleware (proxies, browser) should never serve stale snapshots. | REST telemetry hygiene |
| D11 | **`is_recent(emhass_conf, max_age_seconds)` helper exported from module** even though only AC-3 ships in this PR. AC-4 (already Todo) will import it for `/healthz`; pre-declaring the API stabilizes the contract. | counter-future-friction |
| D12 | **Stage_times keys come from existing `stage_timer` calls** in `_prepare_*_optim` helpers (verified: `pv_forecast` at line 758, `load_forecast` at line 763 of `command_line.py`). No new stages added in this PR. Future stages added by extending the timer wrappers, recorded automatically. | item body + source-trace |
| D13 | **URL versioning: `/api/v1/...` from day 1.** AC-3 establishes the `/api/*` prefix on the EMHASS web_server (existing legacy `/get-*` / `/set-*` routes stay untouched, no version). All `/api/*` endpoints adopt `v1` baseline. Future breaking changes bump URL to `v2/` with co-existing `v1` until sunset. Orthogonal to `schema_version` in the response body (URL versions the surface, body versions the shape — paired major-bumps when both change). | session 2026-05-11 |
| D14 | **JSON-Schema sidecar file** at `docs/api/v1/last-run.schema.json` documents the response shape. Hand-authored JSON Schema draft 2020-12. Consumer ecosystem (Pydantic validation, TypeScript code-gen, OpenAPI tooling) reads the sidecar directly. AM-1's future generator pipeline ingests this file plus param_definitions.json + plan_output_schema.md to emit the full openapi.json. AC-3 does NOT ship openapi.json itself — that's AM-1's deliverable. | AM-1 dependency direction |
| D15 | **AM-1 dependency-chain awareness.** AM-1 (openapi.json + generator) depends on AC-1 + AC-2a + AC-2b. AC-3 also depends on AC-1 (D5). AM-1 cannot ship before AC-3 because its dependency chain is longer. AC-3 prepares for AM-1 by writing the schema sidecar in a generator-readable form; no retrofit needed when AM-1 lands. | AM-1 body item; sequencing logic |

## 6. Test strategy

- **Unit tests on `last_run.py` module** — primary verification. Pure-Python module, no Flask, fast (<1s). Covers record/read/is_recent contract, thread-safety, corruption recovery.
- **Integration tests via Flask test_client** — 2 tests in `tests/test_web_server.py`. Reuse existing fixtures (test_df, sample config) so the test suite picks them up automatically. Verifies route registration + response shape + 200 always.
- **No real solver invocation in tests** — mock optim path or use existing fixture-based test pattern. Solver runs are slow + nondeterministic.
- **Manual smoke check** — `curl http://localhost:5000/api/v1/last-run` before first run (expect `status: no-run`), trigger an optim, curl again (expect `status: ok` with stage_times populated).

## 7. Acceptance criteria

1. `src/emhass/last_run.py` exists with `record()`, `read()`, `is_recent()`, and internal helpers. All three public functions documented with docstrings.
2. `GET /api/v1/last-run` returns 200 with `Content-Type: application/json` and `Cache-Control: no-store` always.
3. Response shape: 9 fields per D4; nullable when `status == "no-run"`.
4. Status field is one of `{"no-run", "ok", "infeasible", "error"}`. No other values returned.
5. `command_line.py` action wrappers (`dayahead_forecast_optim`, `naive_mpc_optim`, `perfect_optim`) call `last_run.record(...)` at their successful return path. record-failure does NOT propagate into the action return.
6. Module is thread-safe under multi-worker Flask (lock guards in-memory cache + file write).
7. `<data_path>/last_run.json` is written after every recorded run, contains the same dict the endpoint returns.
8. Unit tests in `tests/test_last_run.py` cover record/read round-trip, no-run reads None, thread-safety smoke (100 records × 10 threads converge to consistent state), corrupted file recovery.
9. Integration tests in `tests/test_web_server.py` cover GET-before-run (status=no-run) and GET-after-naive-mpc-optim (status=ok with stage_times populated).
10. PR body declares dependency on PR #835 (AC-1 `EMHASS_SCHEMA_VERSION`) and references Discussion #808 threat-model agreement.
11. `schema_version` field in response reads from `from emhass.command_line import EMHASS_SCHEMA_VERSION` (post-#835-merge).
12. No new auth, no new FS-write paths beyond `last_run.json`, no shell-out, no dynamic-code execution — confirmed in PR body security-pitch.
13. URL prefix is `/api/v1/` (not `/api/`). Establishes versioning convention for all future `/api/*` endpoints (AC-4, future /api/v1/last-plan, etc.). Per D13.
14. `docs/api/v1/last-run.schema.json` exists, is valid JSON Schema draft 2020-12, and matches the response shape returned by the endpoint for all 4 `status` values. Per D14.

## 8. Out of scope

- **`/healthz` endpoint** — that is AC-4, separate PR. AC-3 exports `last_run.is_recent()` which AC-4 will import, but the endpoint itself is AC-4's deliverable.
- **Full `openapi.json` generation** — that is AM-1, separate PR. AM-1 depends on AC-1 + AC-2a + AC-2b + AC-3's sidecar schema. AC-3 ships only its own sidecar (`docs/api/v1/last-run.schema.json`), AM-1 will aggregate all per-endpoint sidecars + param_definitions.json + plan_output_schema.md into the unified openapi.json.
- **`/api/v1/last-plan` endpoint** (plan-data JSON return) — separate future board card. Plan data accessible today via existing `POST /get-json` route; new `GET /api/v1/last-plan` will pair naturally with `/api/v1/last-run` once added as its own item.
- **`/metrics` endpoint or Prometheus integration** — separate future concern.
- **Historical run log** (last N runs) — AC-3 keeps only the most recent. Multi-run history is a different feature, would need DB or rotating log file.
- **Auth on /api/v1/last-run** — keep consistent with the rest of web_server (no auth today). Adding auth selectively to one endpoint is out of scope.
- **Streaming / SSE / WebSocket updates** — pull-based GET only. Push-based notification is a different surface.
- **Schema-evolution beyond the 9 fields** — v1.0 ships the agreed shape. New fields are minor-bumps per AC-1 semver, future PRs.
- **CLI command to query last_run** (e.g. `emhass --action last-run`) — out of scope; Flask endpoint covers the consumer use cases.
