## 1. Problem

EMHASS publishes 11 fixed columns plus four variable column groups (`P_deferrable{k}`, `predicted_temp_heater{k}`, `heating_demand_heater{k}`, `cost_fun_<name>`) in every optimization result. Downstream consumers (Node-RED EVCC adapter, HA cards, the planned EMHASS-plan-explain LLM skill, third-party automations) reverse-engineer this schema by reading `command_line.py` or guessing from column names. Sign conventions for power columns (`P_grid`, `P_batt`, `P_PV`, `P_PV_curtailment`, `P_hybrid_inverter`) are not declared anywhere consumer-visible. The HA-scaling trap for `SOC_opt` (CSV holds fraction 0..1, HA receives ×100 percent) is undocumented. There is no schema-version constant, so consumers cannot pin against a known column-set generation.

## 2. Goal

Ship a single PR that gives downstream consumers a contract: `docs/plan_output_schema.md` listing every published column with unit, sign convention, conditional presence, HA-scaling note, and source helper, plus a top-level `EMHASS_SCHEMA_VERSION = "1.0"` constant in `command_line.py` attached to the result envelope so consumers can version-pin. Seven sign-convention questions are flagged inline in the doc and surfaced in the PR description for maintainer confirmation; consumers can then trust the schema rather than reverse-engineering it.

## 3. Decisions

| # | Decision | Source |
|---|----------|--------|
| D1 | Single PR carries both the doc and the `EMHASS_SCHEMA_VERSION` constant; no split. Constant is trivially short, doc references it. Splitting would force the maintainer to context-switch twice on the same audit. | audit §6 |
| D2 | Initial version string is `"1.0"`, not `"0.1"`. Prior consumer code already depends on the schema in production; this audit just formalizes it. Locking 1.0 establishes the contract retroactively. | audit §6 |
| D3 | Schema-version attachment surface: `opt_res.attrs["emhass_schema_version"]` on the result DataFrame (pandas `attrs` dict), plus include in the dict returned alongside. Additive on both surfaces; consumers can read either. Final choice deferred to PR review — both are presented. | audit §6 |
| D4 | Sign conventions are NOT guessed in the doc. Each ambiguous column is marked with `(sign convention: TBD — see PR comment)` and the seven open questions go in the PR body as a numbered list for maintainer to answer per-line. Once answered, doc gets a follow-up patch on the same branch before merge. | `feedback_no_auto_bugfix`, audit §4 |
| D5 | Semver rules for the constant go in the doc itself (not just commit message): patch = doc clarification, minor = additive column, major = remove/rename/flip-sign/unit-change/HA-scaling-change. | audit §6 |
| D6 | Conditional-presence flags (`SOC_opt` only if `set_use_battery=true`; `P_PV_curtailment` only if `plant_conf.compute_curtailment=true`; etc.) are explicit in the table, not in prose. Consumers grep the table. | audit §3 |
| D7 | `SOC_opt` HA-scaling trap gets its own callout box in the doc, not just a table cell. Wrong scaling is the most likely consumer bug. | audit §2 (battery section) |
| D8 | Doc is plain Markdown table + prose, no Sphinx directives. EMHASS docs site renders Markdown directly. Keeps the doc readable as raw file on GitHub too. | EMHASS repo docs/ convention |

## 6. Test strategy

This is a documentation + single-constant PR. No new code paths, no new logic.

- **Doc lint:** Markdown renders correctly on GitHub preview. Table renders. Internal anchor links resolve. No dead links.
- **Code lint:** `EMHASS_SCHEMA_VERSION` constant is referenced, not orphaned. `opt_res.attrs` write does not break existing pandas serialization (CSV write drops `attrs` by design; JSON export via `to_dict` ignores `attrs` — confirm no result consumer relies on `attrs` being absent).
- **Smoke run:** Manually run one optimization end-to-end against a small config; verify a published result CSV column-set matches the doc and that `result.attrs["emhass_schema_version"] == "1.0"` is readable from a follow-up `pd.DataFrame` reference in the same Python session.
- **No automated test added.** The doc is the test artifact; the constant is one line. Adding a unit test for "string equals 1.0" is noise. If the maintainer requests one, add `tests/test_schema_version.py` with a single assertion.

## 7. Acceptance criteria

1. `docs/plan_output_schema.md` exists with all 11 fixed columns + 4 variable groups documented; each row has name, unit, sign convention (or TBD marker), conditional flag, HA-scaling note, source helper, type_var tag.
2. `EMHASS_SCHEMA_VERSION = "1.0"` constant exists in `command_line.py`; doc references it.
3. Constant is attached to result envelope via `opt_res.attrs["emhass_schema_version"]` and/or the returned dict.
4. Semver rules (patch / minor / major) are documented inside the schema doc.
5. SOC_opt HA-scaling trap has its own callout.
6. PR body lists the 7 sign-convention open questions as a numbered list addressed to `@davidusb-geek`.
7. Doc nav entry (if applicable) added to `mkdocs.yml` or equivalent.
8. Maintainer can review the doc + constant in under 15 minutes without needing to read the audit.

## 8. Out of scope

- Resolving the 7 sign-convention questions in this PR. They are surfaced for maintainer; once answered, a follow-up patch on the same branch closes them before merge.
- Refactoring the 5 `_publish_*` helpers themselves. They stay as-is.
- New columns. The schema documents what exists today.
- LLM-skill integration. AC-1 unblocks future work but does not consume the doc itself.
- Input-side schema (`param_definitions.json`). That is the sibling audit, separate concern, no overlap with this PR (verified — no key overlap with PR #830).
- Cross-link audit in every `docs/study_cases/*.md`. Optional, skip if not natural.
