## Root cause

PR #845 changed four `config_defaults.json` values to align with `param_definitions.json` per maintainer's Option-B decision:

| Key | Pre-#845 | Post-#845 |
|---|---|---|
| `historic_days_to_retrieve` | 9 | 2 |
| `load_forecast_method` | `"naive"` | `"typical"` |
| `inverter_ac_output_max` | 5000 | 0 |
| `inverter_ac_input_max` | 5000 | 0 |

Reverting all four locally on current master, the test passes (4 active timesteps for load 0). Reverting each value in isolation:

- `load_forecast_method` alone reverted to `"naive"` → test passes (4 timesteps).
- The other three reverted individually → test still fails (5 timesteps).

So the single root cause is the `load_forecast_method` default change from `"naive"` to `"typical"`.

## Mechanism

`test_load_deactivation_zero_operating_timesteps` calls `perform_naive_mpc_optim()` with manually-injected `p_load_forecast` via `prepare_forecast_data()`. The injected forecast is the same in both runs. But `load_forecast_method` is also read during optim setup (`get_yaml_parse → optim_conf`) and reaches downstream load-curve shaping somewhere in the MILP build path. The resulting load-curve difference drives a different optimum, which puts deferrable load 0 across 5 timesteps instead of 4.

I have not traced the exact code path inside `optimization.py` that consumes `optim_conf["load_forecast_method"]` after a forecast is injected. The above is empirical isolation only.

## Verdict

Intentional behavior change, not a regression bug. PR #845's commit body acknowledges:

> Behavior change for Headless users (no GUI config save) on these four parameters.

The test was passing before #845 because the `"naive"` default produced a specific load-curve that satisfied the 4-timestep expectation. The test was not pinning `load_forecast_method`, so it inherited whatever default was in `config_defaults.json` at test time. After #845, the inherited default is `"typical"`, the load-curve differs, and the assertion no longer matches.

## Proposed fix

Pin `load_forecast_method` explicitly in the test fixture, so the test asserts against a known forecast method regardless of future default shifts:

```python
self.optim_conf.update(
    {
        "set_use_battery": True,
        "treat_deferrable_load_as_semi_cont": [True, True],
        "set_deferrable_load_single_constant": [True, True],
        "load_forecast_method": "naive",  # ← pin to keep assertion stable
    }
)
```

Effect:
- Test asserts deterministic behavior against `"naive"` load forecast.
- Future `config_defaults` default-shifts don't break the test.
- The 4-timestep expectation stays valid with its pre-#845 semantics.

Alternative: update the assertion to expect 5 and re-document the test under `"typical"` semantics. Pinning is preferable. The test then survives any future default re-tune in either direction.
